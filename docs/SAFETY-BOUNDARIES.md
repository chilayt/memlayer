# 安全与撤回边界（必读）

> 核心结论：**撤回召回 ≠ 彻底遗忘。** 把二者等同是误导。

## 撤回能做到
- 标记事实已撤回（墓碑），后续召回不再返回。
- 撤回账本（谁/何时/撤了什么），可审计。
- 同源级联：撤回来源时联动撤回派生事实。
- 备份恢复后重放账本，防已撤事实复活。
- 撤回钩子清理嵌入缓存向量（含级联）。

## 撤回做不到（残留风险）
以下副本可能仍含原文，撤回无法触及：
1. 历史备份（撤回前的备份）。
2. Git 历史（若台账进过 git）。
3. 日志（注入审计/调试日志可能记录过）。
4. 已发给模型的上下文（先前对话已在模型/服务端历史）。
5. 下游副本（任何复制/导出过的地方）。
6. 嵌入服务商侧（已外发的文本，按其保留政策）。

**撤回 = 之后不再主动召回，不是「世上不再有这段内容」。不满足严格被遗忘权。**

## 外发告知
外部嵌入默认关闭，需要显式设置 MEMLAYER_EMB_KEY 才能启用该后端。启用后，查询及候选事实文本会发给嵌入服务商，含 shadow 模式。本机 ONNX 方案在本机计算召回。上层应用按其模型配置使用最终入选的记忆。

## 持久化边界
save = fsync + os.replace：保证原子性+刷到 OS。对已成功持久化的撤回记录、存储未损坏、重放成功的前提下，重启/崩溃不复活。**不承诺绝对断电持久性**（依赖文件系统/硬件）。

## 审批门风险
人工审批是信任基石，但量大时会审批疲劳→盲签，「已批准」标签可能给恶意内容洗白。审批不能替代内容校验。

## 法律
删除/被遗忘义务因法域而异（GDPR vs PIPL 等）。本文不是法律意见，不构成合规认定。

## 本机客户端

任何能访问这个端口的本机进程都可调用 API，并访问该实例中的项目数据。请给不同用户分配独立的系统账户或运行环境。桥拒绝来自网页 Origin 或非本机 Host 的请求。DSH 的采集需要显式开启并限定项目，影子日志和未投递队列仍可能包含原话。
